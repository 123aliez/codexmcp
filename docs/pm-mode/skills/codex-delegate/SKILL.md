# 委派给 Codex 并验收

## 1. 选沙箱

| 任务 | `sandbox` |
|---|---|
| 读代码、定位 bug、评审、出实现方案 | `read-only`（默认，Codex 不能改文件） |
| 实现、修复、跑测试 / 构建 | `workspace-write` |
| `danger-full-access` 或 `yolo` | 仅在用户明确要求时 |

- `cd` 填项目根目录的绝对路径。
- 不传 `model` / `profile`，除非用户指定。
- 不开 `return_all_messages`：它返回全部原始事件，通常有上万 token；返回值里的证据字段已够验收用。
- 长任务可调 `timeout`（秒，默认 3600）。

## 2. 写任务书（PROMPT）

按下面的结构写。越具体，返工越少：

```
目标：<一句话>
背景：<相关文件 / 函数 / 已知约束，给出路径>
范围：只允许改 <文件或目录>；禁止改 <...>；不新增依赖（除非写明）
完成标准：<验收命令> 通过，且 <期望行为>
回报（不超过 30 行）：
- 每个改动文件一句话：改了什么、为什么
- 跑了哪些命令、结果如何
- 未完成项 / 需要 PM 决策的问题
```

大任务分两步：先派一个 `read-only` 调研拿到方案，你确认后，再在**同一个 SESSION_ID** 上用 `workspace-write` 让它实现。

## 3. 读返回值

- `success=false`：先读 `error`。超时也会带回 `SESSION_ID` 和超时前的改动；先看 `files_changed`，再决定续接还是回滚。
- `agent_messages`：Codex 的最终回复，即它的自述，需要和下面两项对照。
- `files_changed`：Codex 用补丁工具改过的文件。**shell 命令（格式化、代码生成、`sed -i`）改的文件不会出现在这里**，所以范围核对以 git 为准。
- `commands`：Codex 实际跑过的命令和退出码，失败的会带 `output_tail`。用它核对测试有没有真的跑过、有没有通过。

## 4. 验收清单

1. `git status --short` 和 `git diff --stat`：确认改动没有超出任务书的范围。
2. 只看关键文件的 diff，不通读整个文件。
3. 亲自跑一次完成标准里的验收命令，只看退出码和摘要（例如 `pytest -q 2>&1 | tail -5`）。
4. 不合格：用同一个 `SESSION_ID` 续接，只写"差距 + 期望"，不重复整份任务书。
5. 同一任务连续 2 轮不合格，停下来向用户说明情况，给出可选方案。
6. 合格后向用户汇报：完成了什么、验收依据（命令和结果）、遗留问题。

## 5. 并行

互不相关的 `read-only` 调研可以并行发起。不要让两个 `workspace-write` 调用同时改同一批文件。

# 委派给 Codex 并验收（PM 模式）

你是 PM：写任务书、委派、验收，不亲自改代码。下文的 `<项目>` 指项目根目录（项目 git 仓库的根目录）的绝对路径。

如果当前工作区的规则（`CLAUDE.md` 及其导入的文件）对确认流程、项目约定文档、进度台账另有规定，以工作区规则为准。本 skill 只规定委派和验收本身。

## 0. 开工前

1. 找到项目的约定文档，例如 `AGENTS.md`、`PROJECT.md` 里的开发约定、`README` 的开发章节，从中获取技术栈、测试命令和禁区。找不到测试命令时，先问用户。
2. 运行 `(cd <项目> && git status --short)`。工作区不干净时，先问用户是否提交，保证验收时 diff 里只有本次改动。

本 skill 里的命令都放在 `( ... )` 子 shell 里执行，这样 `cd` 不会改变会话的工作目录。

## 1. 选沙箱

| 任务 | `sandbox` |
|---|---|
| 读代码、定位 bug、评审、出实现方案 | `read-only`（默认，Codex 不能改文件） |
| 实现、修复、跑测试 / 构建 | `workspace-write` |
| `danger-full-access` 或 `yolo` | 仅在用户明确要求时 |

- 工作区规则要求"改文件前先给计划、等确认"时，`workspace-write` 委派前先把任务书发给用户确认；同一任务在已确认范围内的返工不必再问。
- `cd` 填 `<项目>`。
- 不传 `model` / `profile`，除非用户指定。
- 不开 `return_all_messages`：它返回全部原始事件，通常有上万 token，返回值里的证据字段已够验收用。
- 长任务可调 `timeout`（秒，默认 3600）。
- Codex 沙箱默认没有网络。需要装依赖时，由你把安装命令交给用户确认后自己执行，不交给 Codex。

## 2. 写任务书（PROMPT）

第一行固定写「【任务书】」。它表示这是非交互执行：Codex 应直接动手、不要反问；项目的 `AGENTS.md` 如果定义了执行者模式，也以这个标记识别。

```
【任务书】
项目：<项目名>。开工前先读 <约定文档路径>。
目标：<一句话>
背景：<相关文件 / 函数 / 已知约束，给出相对项目根的路径>
范围：只允许改 <文件或目录>；禁止改 <...>；不新增依赖（除非写明）
完成标准：<验收命令> 通过，且 <期望行为>
要求：<工作区对代码的通用要求，例如注释语言；以及不许碰的文档或台账>
回报（不超过 30 行）：
- 每个改动文件一句话：改了什么、为什么
- 跑了哪些命令、结果如何
- 未完成项 / 需要 PM 决策的问题
```

大任务分两步：先派一个 `read-only` 调研拿到方案；确认后，在**同一个 SESSION_ID** 上用 `workspace-write` 让它实现。

## 3. 读返回值

- `success=false`：先读 `error`。超时也会带回 `SESSION_ID` 和超时前的改动，先看 `files_changed`，再决定续接还是回滚。
- `agent_messages`：Codex 的最终回复，即它的自述，要和下面两项对照着看。
- `files_changed`：Codex 用补丁工具改过的文件。**shell 命令（格式化、代码生成、`sed -i`）改的文件不会出现在这里**，所以核对改动范围以 git 为准。
- `commands`：Codex 实际跑过的命令和退出码，失败的会附 `output_tail`。用它核对测试有没有真的跑过、有没有通过。

## 4. 验收清单

1. `(cd <项目> && git status --short && git diff --stat)`：确认改动没有超出任务书的范围。
2. 只看关键文件的 diff（`(cd <项目> && git diff -- <文件>)`），不通读整个文件。
3. 亲自跑一次测试命令，只看结果摘要：`(cd <项目> && <测试命令>) 2>&1 | tail -5`。
4. 不合格：用同一个 `SESSION_ID` 续接，只写"差距 + 期望"，不重复整份任务书。
5. 同一任务连续 2 轮不合格，停下来向用户说明情况，给出可选方案。
6. 合格后向用户汇报：完成了什么、验收依据（命令和结果）、遗留问题、`SESSION_ID`。工作区有进度台账的，按工作区规则询问是否记录（建议格式：`codex:<SESSION_ID>`）。

## 5. 并行

互不相关的 `read-only` 调研可以并行发起。不要让两个 `workspace-write` 调用同时改同一个项目里的同一批文件。
